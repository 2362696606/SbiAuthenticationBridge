# Plan:CTK 验证与修复（第 5 轮）

> 对应 spec：`specs/20261026-CTK验证并修复-5.spec.md`
> 依据：本次文件日志中 FAP20 原始收发记录、CTK SBI1018 结果、参考 sbi-bridge 的响应缓冲处理。

## 0. 日志实证

SBI1018 本次请求（`Logs/sbi-20261026_001.log`）：

```text
17:48:45.955 ftm_capture_auth 响应 rc=0x0 TEXT={"biometrics":[{...
  "thumbprint":"F93E...","error":{"errorCode":"0","errorInfo":"Success"}}]}2
17:48:46.031 CAPTURE 完成：bio 项数=1，返回条数=1
17:48:46.034 CAPTURE 响应体：{"biometrics":[...,"error":{"errorCode":"110","errorInfo":"Device is not ready"}}]}
```

固件已经采到手指并返回成功 JWT，但主机把响应解析成了 110。

把日志中的 TEXT 交给 JSON 解析器：

```text
Extra data: line 1 column 26773 (char 26772)
```

即 JSON 末尾多了一个残留字节 `2`。

## 1. 根因

1. `FAP20` 的响应缓冲区由 `Marshal.AllocHGlobal(ResponseBufferSize)` 分配，
   **未清零，SDK 也不保证 NUL 结尾**。
2. 短响应（101）覆盖不了上一轮遗留的数据；成功采集的 JSON 后面跟着残留字节。
3. `FtmProtocolCodec.TrimAtNul` 只能截到第一个 `0x00`；
   若残留字节非零，就会拼进 JSON。
4. `ParseBiometric` 抛 `JsonException`，被 `TryCaptureOnceAsync` 当作设备失败，
   映射为 **110**——业务层看到“Device is not ready”，实际采集已成功。

这与参考实现中“每次调用前清空 respBuf，防止旧响应残留导致 JSON 拼接错误”一致。

### 1.1 补充：`ftm_load_certificate` 返回 0x75

文件日志中 4 次出现：

```text
18:06:33.947 ftm_load_certificate 响应 rc=0x75 34B HEX=0000...
18:06:54.787 向设备 FAP20Proxy 加载域加密证书失败
FtmCommandException: ftm_load_certificate 失败，返回错误码 0x75（117）
```

- 设备刚完成 `MOSIPDINFO`，3 秒后 `LOAD_CERTIFICATE` 仍返回 `0x75`（DEVICE_BUSY）
- `ThrowIfFailed` 已执行 `ftm_device_reset(2000)`，但日志显示复位实际阻塞约 21 秒，
  远超 CTK 的 10 秒采集超时
- 当前采集轮询把 `0x75` 映射成 111，不会继续重试；而每次 CAPTURE 前都下发证书，
  导致每次都可能再次撞上 `0x75`

参考项目对 `0x75` 的处理：

- 所有 DLL 封装方法统一检测 `0x75` 并调用 `ftm_device_reset(2000)`
- 当前命令仍按失败返回，不自动重发
- 域证书只在设备连接或手动操作时下发，不在每次 CAPTURE 前下发

## 2. 修复

### 2.1 响应缓冲区每次调用前清零

`SbiAuthenticationBridge.Device/FAP20.cs`：

```csharp
private static readonly byte[] ZeroResponseBuffer = new byte[ResponseBufferSize];

private static IntPtr AllocateResponseBuffer()
{
    var pointer = Marshal.AllocHGlobal(ResponseBufferSize);
    Marshal.Copy(ZeroResponseBuffer, 0, pointer, ResponseBufferSize);
    return pointer;
}
```

- 将 8 处 `Marshal.AllocHGlobal(ResponseBufferSize)` 全部替换为 `AllocateResponseBuffer()`：
  - LoadCertificate、Discover、DeviceInfo、CaptureAuth、CaptureReg
  - GetDklPublicKey、SetDklCertificate、Recv
- 请求缓冲区保持原样。

### 2.2 采集轮询把 0x75 当作可重试

`SbiAuthenticationBridge.Device/FAP20Proxy.cs`：

- `TryCaptureOnceAsync` 增加与 -7 同级的前置捕获：

  ```csharp
  catch (FtmCommandException exception)
      when (exception.ResultCode == FAP20.DeviceBusyResultCode)
  {
      // ThrowIfFailed 已执行软复位，本轮继续等待手指
      return null;
  }
  ```

- 与参考实现一致：复位后继续轮询，而不是把 111 返回给 CTK。

### 2.3 域证书下发遇到 0x75 重试一次

`SbiAuthenticationBridge.Device/FAP20Proxy.cs`：

- `LoadDomainEncryptionCertificateAsync` 捕获 `0x75`：
  1. `ThrowIfFailed` 已完成软复位；
  2. `Task.Delay(500ms, cancellationToken)`；
  3. 重新下发一次完整证书；
  4. 再次失败才向上抛出。
- 重试只针对 `0x75`，其他错误不重试。

### 2.4 域证书改为每个设备会话下发一次

`SbiAuthenticationBridge.Host/SbiAuthenticationServiceHandle.cs`：

- 使用 `ConcurrentDictionary<ISbiDevice, byte>`（引用相等）记录已成功下发证书的设备；
- `PrepareDeviceAsync`：
  - 已记录 → 直接返回，不再每条采集都发 `LOAD_CERTIFICATE`；
  - 未记录 → 下发成功后记录；
- 采集返回 **108（缺域证书）** 时：
  - 强制重新下发一次域证书；
  - 重新执行一次该 bio 的设备采集；
  - 仍为 108 才把错误返回 CTK。

这样：

- 正常 CTK 会话只下发一次证书，显著降低撞上 `0x75` 的概率；
- 设备重连、复位后 RAM 证书丢失时，由 108 自动补发；
- SBI1024 密钥轮换后如果清掉域证书，也会由 108 自动补发。

### 2.5 不修改

- 不改 JSON 解析、DTO、SBI 路由；
- 不改 -7 重试、SBI 错误码映射、超时策略；
- 不新增 NuGet。

## 3. 文件清单

| 文件 | 改动 |
|---|---|
| `SbiAuthenticationBridge.Device/FAP20.cs` | 新增清零响应缓冲区分配方法，替换 8 处分配 |
| `SbiAuthenticationBridge.Device/FAP20Proxy.cs` | 采集轮询重试 0x75；域证书下发 0x75 重试一次 |
| `SbiAuthenticationBridge.Host/SbiAuthenticationServiceHandle.cs` | 域证书按设备会话缓存；108 时强制补发并重试采集 |

## 4. 架构与依赖自查

- `FAP20` / `FAP20Proxy` 改动位于 Device 层；
- `SbiAuthenticationServiceHandle` 只依赖 Core 的 `ISbiDevice`、`IFtmSecureDevice`，
  不引用 Device 实现，符合 arch.md；
- 不吞异常：0x75 仅在确认已软复位后转为“重试”，最终失败仍会上报；
- 不改变线程模型与锁顺序。

## 5. 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| 每次命令多一次 200KB 清零拷贝 | 低 | 微秒级，远小于 USB 命令耗时 |
| 固件响应本身包含合法的 `0x00` | 低 | 现有协议响应均为文本 JSON 或定长二进制帧 |
| 0x75 软复位可能阻塞约 21 秒 | 中 | 已超过 CTK 10 秒超时；减少下发次数后影响面显著缩小，单次仍可能超时 |
| 证书缓存与设备实际状态不一致 | 低 | 108 会强制补发；设备重连后首次采集即可自愈 |
| 108 重试导致一次采集变慢 | 低 | 仅异常路径，最多一次重试 |
| 修复后 1069/1082/1090/1107 仍失败 | 中 | 这 4 个用例额外校验 ISO/质量/时间/hash，需真实成功响应后继续定位 |

## 6. 验证方式

1. 构建 Desktop。
2. 重启应用，发起一次真实认证采集：
   - 固件原始响应末尾不再有残留字节；
   - HTTP 响应 `errorCode=0`，包含 `data/hash/sessionKey/thumbprint/dataDecoded`。
3. 连续执行多次 CAPTURE，确认日志中 `ftm_load_certificate`：
   - 同一设备会话只出现一次成功下发；
   - 只有首次或收到 108 时才重新下发。
4. 人为制造 0x75（或在日志中等待复现）：
   - 采集请求不再直接返回 111；
   - 日志显示复位后继续轮询。
5. 重跑 CTK：
   - SBI1018-1021 应通过；
   - 继续查看 1069/1082/1090/1107 的 validator 文案。
