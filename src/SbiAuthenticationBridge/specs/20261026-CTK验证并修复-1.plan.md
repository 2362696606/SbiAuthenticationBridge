# Plan:CTK 验证与修复（第 1 轮）

> 对应 spec：`specs/20261026-CTK验证并修复-1.spec.md`
> 依据：CTK 官方 testcase 定义（`mosip/compliance-toolkit-testcases`）、CTK SBI 0.9.5 JSON Schema、真实 FAP20 诊断输出。
> 设备注册状态按已确认方案处理：**外部恢复注册**；本次只修协议/字段/错误码等代码问题。

## 0. 诊断结论

> 编码期间设备已由外部恢复为 Ready/registered：最新真实 Discover/Info 返回 `deviceStatus=Ready`、
> `purpose=Auth`、`deviceSubId=["0"]`、`error=0/Success`，签名 JWT 正常。下面保留初始诊断记录用于说明根因。

### 0.1 真实设备响应（FAP20，初始状态）

```json
// DISCOVER
{
  "deviceId": "ICT-35195E304B513335",
  "deviceStatus": "Not Registered",
  "certification": "L1",
  "serviceVersion": "0.9.5",
  "deviceSubId": [],
  "callbackId": "http://127.0.0.1:4501",
  "digitalId": "<未签名 base64 payload>",
  "deviceCode": "ICT-35195E304B513335",
  "specVersion": ["0.9.5"],
  "purpose": "",
  "error": { "errorCode": "100", "errorInfo": "Device not registered" }
}

// INFO
{
  "deviceInfo": "<未签名 base64 payload，deviceStatus=Not Registered>",
  "error": { "errorCode": "100", "errorInfo": "Device not registered" }
}

// CAPTURE count=11
{
  "biometrics": [{
    "specVersion": "0.9.5",
    "data": "", "hash": "", "sessionKey": "", "thumbprint": "",
    "error": { "errorCode": "501", "errorInfo": "Invalid capture protocol" }
  }]
}
```

### 0.2 根因

**设备当前为 Not Registered / 未签名状态**。CTK 测试定义显示：

| 用例 | 响应 Schema / 校验器 | 当前失败原因 |
|---|---|---|
| SBI1000 / SBI1001 | `DiscoverResponseSchema` / `DeviceInfoResponseSchema` + **SignatureValidator** | 设备未注册，`digitalId`/`deviceInfo` 未签名，`error=100`、`purpose=""` |
| SBI1026 / SBI1024 | `DeviceInfoReadyResponseSchema` + Signature/KeyRotationValidator | 设备非 Ready |
| SBI1018-1021、1057、1069、1082、1090、1107 | `AuthCaptureResponseSchema` + SignatureValidator | 设备未注册，采集返回错误；且成功响应缺少 `dataDecoded` |
| SBI1027-1029 / 1048 / 1093 / 1196 | Busy/NotReady/NotRegistered/错误响应 Schema | 这些是错误/负向路径，正好与当前 Not Registered 状态匹配，因此通过 |

**结论：成功类用例无法在未注册设备上通过，代码修复不能替代设备注册。** 设备需外部恢复到 Ready/registered（已确认）后重跑 CTK。

### 0.3 CTK Schema 与当前实现的确定差异

1. **成功响应 `error.errorInfo` 必须为 `"Success"`**；固件成功响应可能返回 `errorInfo: ""`，当前 `ReadError` 原样透传 → Schema 失败。
2. **Discover `deviceSubId` 必须是字符串数组**（`"0".."3"`）；当前 DTO 为 `int`，序列化为数字 → Schema 失败。空数组还会违反 `minItems: 1`，应省略。
3. **`deviceStatus` 只允许 `Ready/Busy/Not Ready/Not Registered`**；固件可能返回 `"Normal"`，当前透传 → 失败。
4. **Auth Capture 成功响应必须包含 `dataDecoded`**（解码后的 Capture JWT + `digitalIdDecoded`，`requestedScore/qualityScore` 为字符串）；当前 `BiometricInfo` 没有该字段 → 所有成功采集用例 Schema 失败。
5. **SBI1030（bioCount=11）要求错误码 109 + 固定描述**；固件返回 `501 Invalid capture protocol`，当前透传 → 失败。
6. **SBI1024 Key Rotation**：应用侧 GET 公钥 → 本地签发 → SET 证书的流程与参考文档一致；当前失败由设备非 Ready 导致。恢复注册后按 CTK 提示操作验证。

## 1. 代码修复

### 1.1 成功错误对象归一化（`FAP20Proxy.ReadError`）

- `errorCode` 缺失/为空/`"0"` → 返回 `SbiErrorHelper.Success`（`errorCode=0`、`errorInfo=Success`）。
- 非 0 错误：`errorInfo` 为空时补一个非空通用描述（避免 CTK 错误 Schema 的非空校验失败）。
- 影响 Discover / Info / Capture 全部响应。

### 1.2 Discover 字段修正

- `DiscoveryResponse.DeviceSubId` 类型改为 `IReadOnlyList<string>?`。
- `FAP20Proxy.ParseDiscoveryResponse` 使用 `ReadStringArray`（兼容固件返回数字或字符串），空列表置 `null`，由 HTTP 层 `WhenWritingNull` 省略。
- `DeviceStatus` 输出前归一化：`Normal → Ready`、`NotReady → Not Ready`、`NotRegistered → Not Registered`。
- `SbiDeviceSelector` 的 `DeviceSubId` 匹配改为字符串比较。
- 保留固件返回的 `purpose/digitalId/deviceCode/specVersion/callbackId`；注册成功后由固件提供合法值。

### 1.3 Capture 成功响应增加 `dataDecoded`（Auth / Registration 共用）

- 新增 Core DTO `CaptureDataDecoded`（wire shape 严格对齐 CTK）：
  - `digitalId`（原始 JWT/base64 字符串）
  - `digitalIdDecoded`（`DigitalId` 对象）
  - `deviceCode`、`deviceServiceVersion`、`bioType`、`bioSubType`、`purpose`、`env`、`domainUri`、`bioValue`、`transactionId`、`timestamp`
  - `requestedScore` / `qualityScore`（字符串，InvariantCulture）
- `BiometricInfo` 增加 `DataDecoded`：
  ```csharp
  [JsonPropertyName("dataDecoded")]
  [JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]
  public CaptureDataDecoded? DataDecoded { get; set; }
  ```
  - 成功时填充；错误/无 data 时为 `null`，JSON 中省略（错误 Schema `additionalProperties: false`，不能出现 `dataDecoded`）。
  - **Auth 与 Registration 的成功 Schema 都要求 `dataDecoded`**，区别在 `dataDecoded.purpose`（Auth / Registration）与 `bioValue` 是否加密；因此解码逻辑共用。
- `FAP20Proxy.ParseBiometric`：
  1. 仅当 data 非空且错误码为 0 时解码；
  2. 解码 Capture JWT payload → `CaptureData`；
  3. 解码其中的 `digitalId` → `DigitalId`；
  4. 映射为 `CaptureDataDecoded`，分数格式化为 InvariantCulture 字符串；
  5. 原 `data` 字符串保持不变，不重新签名。
- 解码失败不影响采集结果，只是不输出 `dataDecoded`（并写 `Debug` 日志）；CTK 会明确报 Schema 失败。

#### 1.3.1 是否拆分 Auth / Registration 响应类型？

- CTK 两个 Schema 的实际差异：
  - Auth 成功：要求 `sessionKey`、`thumbprint` + `dataDecoded`（`dataDecoded` 必须含 `domainUri`）；
  - Registration 成功/错误：仅允许 `specVersion/data/dataDecoded/hash/error`，**禁止** `sessionKey/thumbprint`；Registration 的 `dataDecoded` **不允许 `domainUri`**（`additionalProperties: false`）；
  - Auth 错误：允许（非必需）`sessionKey/thumbprint`，禁止 `dataDecoded`。
- `BiometricInfo` 本来就是 Auth 字段的“超集 + 可空 + `WhenWritingNull`”。只要：
  - Auth 成功填充 `sessionKey/thumbprint`；
  - Registration 成功/错误保持 `sessionKey/thumbprint = null`，且 `dataDecoded.domainUri = null`；
  - **所有错误 biometric 的 `sessionKey/thumbprint` 改为 null**（当前 `CreateErrorBiometric` 写空串，会在 Registration 错误响应中多出字段）；
  - 错误项 `DataDecoded = null`；
  
  同一个 DTO 就可以序列化出两种合法的 wire shape。
- **本轮建议不拆分 Core/Device 类型**：拆分 `CaptureResponse`/`BiometricInfo` 会同时影响两个设备接口、两个 ServiceHandle 和 Host 合并逻辑，重复字段多、收益仅是编译期约束。
- 若后续需要更强的编译期保证，推荐在 **Host.Http（wire 层）** 增加 `AuthenticationCaptureResponse` / `RegistrationCaptureResponse` 两个响应 DTO，由端点映射后再序列化；不要把拆分扩散到 Core/Device 的服务契约。

### 1.4 BioCount mismatch → 109

- `FAP20Proxy.CaptureCoreAsync` 在进入固件采集前校验每个 bio 项：
  - `count` 显式存在且 `count < 1` 或 `count > 9` → 109；
  - `count` 与 `bioSubType.Count` 同时存在且不相等 → 109；
  - 返回单个错误 biometric，使用 `SbiErrorHelper.RequestedBiometricCountNotSupported`（109 + 固定描述），不再把固件 501 透传给 CTK。
- 其他错误（101/102/112 等）保持原逻辑。
- 所有 `CreateErrorBiometric`（Device 与 Host）中的 `sessionKey/thumbprint` 由空串改为 **null**，确保 Registration 错误 Schema 不会因多余字段失败；Auth 错误 Schema 中两者本来就是可选。

### 1.5 Key Rotation

- 本次不改代码：应用侧流程（GET_DKL1_PUBLIC_KEY → 本地签发 → SET_DKL1_CERTIFICATE）与参考文档一致，且此前已验证证书成功下发。
- SBI1024 依赖 Ready/registered 设备；恢复注册后按 CTK 提示在 ServiceOperate/DeviceOperate 中执行轮换，重新验证。
- 若恢复注册后仍失败，再单独排查证书有效期/KeyUsage/固件切换结果（另立工单）。

## 3. 架构与依赖自查

- Core DTO 变更（`DeviceSubId` 类型、`BiometricInfo.DataDecoded`）属于契约变更，按 arch 标为**中高风险**；仓库内消费方仅 Device/Host/UI，已逐一更新。
- 解码逻辑位于 Device 层（协议/硬件适配），Host 只做合并；不引入新 NuGet。
- 不修改 `data` 原文，不伪造签名、不伪造注册状态。
- 无空 catch；异常路径保留现有日志/错误映射。

## 4. 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| **设备未注册导致成功类用例仍失败** | 高 | 已确认为当前根因；需外部恢复 Ready/registered 后再跑 CTK。代码修复不能替代注册 |
| Core DTO 类型变更 | 中 | `DeviceSubId` 从 int 改 string；仓库内所有使用点同步修改 |
| `dataDecoded` 解码失败 | 中 | 设备 JWT 格式异常时不输出该字段，CTK 会报 Schema；需用真实成功采集验证 |
| 分数序列化为字符串 | 低 | 使用 InvariantCulture，兼容 payload 中数字/字符串两种形态 |
| 错误响应误带 `dataDecoded` | 低 | 属性 `WhenWritingNull`，错误项保持 null |
| Registration 响应误带 `sessionKey/thumbprint` | 中 | Registration Schema `additionalProperties: false`；错误 biometric 的这两个字段改为 null，Registration 成功路径由后续注册设备实现保证不填 |
| bioCount 校验过严 | 低 | 仅在 count 显式存在时校验；与 CTK SBI1030 和 SBI 109 语义一致 |

## 6. 验证方式

1. `dotnet build` 全目标（Shared/Desktop/Android/iOS/Browser）。
2. 真实设备诊断程序：
   - Not Registered 状态下 Discover/Info 仍匹配错误 Schema；
   - Capture count=11 返回 109（不再 501）。
3. 用 Python `jsonschema` 对构造的响应做 Schema 校验：
   - Discover 成功：`deviceSubId` 字符串数组、`deviceStatus=Ready`、`purpose=Auth`、`error=0/Success`；
   - Auth Capture 成功：`dataDecoded` 必填字段、分数为字符串、`sessionKey/thumbprint` 非空、`error=0/Success`；
   - Registration Capture 成功：`dataDecoded.purpose=Registration`，**不出现** `sessionKey/thumbprint`；
   - 错误 Capture / BioCountMismatch：不出现 `dataDecoded`，也不出现 `sessionKey/thumbprint`（Registration 错误 Schema），109 描述正确。
4. 外部恢复设备 Ready/registered 后重跑 CTK，配合真实手指：
   - SBI1000/1001/1026/1024 通过；
   - 采集类用例通过；
   - SBI1030 返回 109；
   - Key Rotation 按 CTK 提示执行后通过。
5. 若恢复注册后仍有失败，用应用日志中的请求/响应体与 CTK 报告逐项定位。
