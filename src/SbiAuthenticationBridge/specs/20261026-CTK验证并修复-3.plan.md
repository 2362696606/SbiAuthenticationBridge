# Plan:CTK 验证与修复（第 3 轮）

> 对应 spec：`specs/20261026-CTK验证并修复-3.spec.md`
> 依据：第三轮 CTK 结果、当前运行服务真实 capture 响应、CTK 校验器源码、参考 sbi-bridge 实现。

## 0. 第三轮现象与根因

### 0.1 已确认修复生效

- SBI1024 Key Rotation **Success**、SBI1026 Ready **Success**：DKL1 叶证书 Subject 已正确
  （当前 `/info` 叶证书 `O=Shenzhen ICT Global, OU=ICT Global-FCG3M, CN=ICT-35195E304B513335`）。
- 因此 SBI1001 与 SBI1018-1021 的失败大概率是它们在 **SBI1024 轮换之前**执行，仍使用旧错误证书；
  当前设备证书已正确，下一次运行（不要再先轮换）应通过。

### 0.2 采集失败的直接原因：SBI 错误码 108

对当前运行服务发起一次真实 Auth capture（真实手指），响应：

```json
{
  "biometrics": [{
    "specVersion": "0.9.5",
    "data": "", "hash": "", "sessionKey": "", "thumbprint": "",
    "error": { "errorCode": "108", "errorInfo": "Missing certificate or key material" }
  }]
}
```

SBI 108 = **Domain public key missing**：设备没有可用的 MOSIP 域加密公钥，无法生成 sessionKey/加密 bioValue。
CTK 的 `AuthCaptureResponseSchema` 要求成功响应，108 直接导致 SBI1018-1021/1057/1069/1082/1090/1107 全部失败。

原因：
- 应用实现了 `FAP20Proxy.LoadDomainEncryptionCertificateAsync`，但**从未调用**；
- 参考 sbi-bridge 使用 `deviceProviderServerCertFile: "key.cer"` 下发域加密证书；
- SBI1024 密钥轮转后，设备的域证书状态可能被清除/失效，之后所有采集返回 108；
- ISO/质量校验器还需要用该证书对应的私钥解密 `bioValue`，证书不对也会失败。

### 0.3 USB -7 超时

SDK 日志频繁出现 `bulk transfer failed ... result=-7`（libusb timeout）。
当前 `FAP20.DefaultTimeoutMs = 1000`，而参考实现 Discover/DeviceInfo 使用 **5000ms**；
默认 1 秒过短，容易在设备忙/轮转后首次命令时超时。

## 1. 修复方案

### 1.1 Auth capture 前加载域加密证书

- 本地 `AppSetting.yaml` 的 `CertificateProvider` 增加：
  ```yaml
  domainEncryptionCertificatePath: ".../device-provider/key.cer"
  ```
  `key.cer` 是 CTK 服务端域加密证书（Subject `CN=COMPLIANCE_TOOLKIT-COMP-FIR`），
  其 SHA-256 为 `F93E60706799FD779BD1E667EDEF50FDB25D71F65CE56F56BC46CD0ED11C4DFF`。
- `SbiAuthenticationServiceHandle` 注入 `ICertificateProvider`；
- 在每次认证 capture 调用设备前：
  ```text
  if device is IFtmSecureDevice && DomainEncryptionCertificate != null:
      await device.LoadDomainEncryptionCertificateAsync(certificate.RawData, ct)
  ```
- **每次采集前都加载**（不做“已加载”缓存）：SBI1024 轮换/设备复位可能清除域证书，
  每次下发可保证后续 CTK 采集不再 108；证书很小，开销可接受。
- 未配置域证书时记录一次 `Warning`；采集仍继续，由设备返回 108。
- 注册采集不需要域证书，不改 `SbiRegistrationServiceHandle`。

### 1.2 延长 USB 超时

- `FAP20.DefaultTimeoutMs`：`1_000` → `5_000`（与参考 Discover/DeviceInfo 的 5s 对齐）；
- `FAP20Proxy.CapturePollTimeoutMs`：`3_000` → `5_000`（单次轮询给设备更多时间，总采集超时仍 30s）；
- 其余证书/复位超时保持不变。

### 1.3 重跑顺序

- 当前设备 DKL1 证书已正确，**下一次 CTK 运行前不要再轮换**；
- SBI1001 与 SBI1018-1021 应在正确证书下通过；
- SBI1024 会再次轮换，之后的采集依赖 1.1 的“每次 capture 前加载域证书”。

## 2. 文件清单

| 文件 | 改动 |
|---|---|
| `SbiAuthenticationBridge.Host/SbiAuthenticationServiceHandle.cs` | 注入 `ICertificateProvider`；每次认证采集前加载域加密证书 |
| `SbiAuthenticationBridge.Device/FAP20.cs` | `DefaultTimeoutMs` 1000 → 5000 |

> 不改 Core 契约、不改 HTTP 路由、不引入 NuGet。

## 3. 架构与依赖自查

- Host 注入的是 Core 的 `ICertificateProvider`，不引用实现包；域证书由组合根提供。
- Device 层只调整超时常量，无新增依赖。
- 证书文件路径属于本地运行配置（gitignore）。
- 不伪造证书、不跳过签名/解密校验。

## 4. 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| `key.cer` 与 CTK KeyManager 的域私钥不匹配 | 中 | 下发后 thumbprint 会变成 `F93E...`；若 CTK 无法解密，需确认 CTK 项目使用的域证书 |
| 每次采集加载证书增加延迟 | 低 | LOAD_CERT 约 1 秒内；CTK 采集总超时 30s |
| SBI1024 轮换后设备仍不清除域证书 | 低 | 每次加载为幂等操作 |
| 延长超时仍无法消除 -7 | 中 | 若 USB 链路本身不稳定，需硬件/驱动层排查 |
| Time/Hash 校验仍失败 | 中 | 取决于固件 timestamp/hash 语义，主机只透传；需真实采集响应进一步确认 |
| 未配置域证书 | 低 | 记录 Warning，设备继续返回 108；本地配置已补 |

## 6. 验证方式

1. 构建 Shared/Desktop/Android/iOS/Browser。
2. 重启应用并连接设备；确认日志出现域证书加载。
3. 发起真实 Auth capture（真实手指）：
   - 不再返回 108；
   - 响应包含 `data/hash/sessionKey/thumbprint`，`thumbprint == F93E...`；
   - `dataDecoded` 存在，schema 校验通过。
4. 查看 SDK 日志，确认 -7 频率下降。
5. 重跑 CTK：
   - SBI1001/1018-1021 使用当前正确证书；
   - 1057/1069/1082/1090/1107 在域证书加载后验证；
   - 如 Time/Hash 仍失败，基于真实响应与 CTK 详细 validator 描述继续定位固件数据语义。
