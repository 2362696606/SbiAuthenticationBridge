# Plan:CTK 验证并修复（第 6 轮）

> 对应 spec：`specs/20261027-CTK验证并修复-6.spec.md`
> 依据：`Logs/sbi-20261027.log` 中 10:20–10:22 的原始收发记录；arch.md。

## 1. 本轮结果与证据

本机日志对应的时间窗口（应用 09:51:23 启动）：

| 用例 | transactionId | 时间 | 设备侧结果 |
|---|---|---|---|
| SBI1069 | SBI1069-402 | 10:20:29–10:20:40 | 全部 101，无成功帧 |
| SBI1082 | SBI1082-49 | 10:20:55–10:21:05 | 全部 101，无成功帧 |
| SBI1090 | SBI1090-84 | 10:21:11–10:21:21 | 全部 101，无成功帧 |
| SBI1107 | SBI1107-242/17/622 | 10:21:32–10:21:58 | 每次请求第 1 轮即成功（约 1.6s） |

统计三个失败用例窗口内的 `ftm_capture_auth`：

```text
固件响应 131 条：全部为 errorCode 101（No finger detected）
rc 全部为 0x0（无 USB 传输错误、无 0x75）
除 101 外没有任何固件错误，也没有任何成功帧
```

结论：

1. **1069/1082/1090 的直接原因是采集窗口内固件持续返回 `101 No finger detected`**，
   即没有拿到任何一帧，服务端没有可校验的数据，只能映射为 102。
2. 紧随其后的 SBI1107 在同一进程、同一设备上三帧全部一次命中，
   说明解析、质量门限、签名、哈希链路当前是正常的。
3. 三个用例本身是交互式采集用例（与 SBI1018-1021 相同），需要在 CTK 提示时按压指纹；
   本轮的 131 次轮询说明按压动作没有发生在这三段窗口内。

## 2. 发现的服务端缺陷（需要修）

`FAP20Proxy.CaptureNormalAsync` 把截止时间设为 **完整的** `timeout`：

```csharp
var deadline = Environment.TickCount64 + timeoutMs;
```

实测 SBI1090：

```text
CTK captureTime            02:21:11.084Z
请求到达服务端              10:21:11.549 (+0.465s)
HTTP 响应完成              10:21:21.550 (请求耗时 10001.76ms)
captureTime → 响应到达     10.466s > timeout(10s)
```

CTK 侧在发送前已有约 0.46s 开销，服务端再用满 10s，响应必然越过
`timeout` 边界。SBI1090 的 `TimeCheckValidator` 校验的正是这个区间，
即便采到合格帧也会被判超时。

## 2.1 关于“失败一律 102”的说明（不修改）

固件错误其实已经透传：`ParseBiometric` → `ReadError` 原样保留 `errorCode`/`errorInfo`，
`CaptureNormalAsync` 对“非 101”的固件错误立即返回，因此 109/110/112/5xx 都会直接进入响应 DTO。

只有以下三种“窗口内没有终态错误可透传”的情况，才在 `CaptureCoreAsync` 合成 102：

| 情况 | 为什么不能透传 |
|---|---|
| 全程只有 101（本轮三个用例） | 101 是“暂未检测到手指”的等待信号；首个 101 就透传会让所有交互式采集在用户按压前立即失败 |
| 采到帧但质量分持续低于 `requestedScore` | 最后一帧是 errorCode 0，透传等于宣告采集成功并交付不合格图像；SBI 0.9.5 没有“质量不达标”错误码 |
| 传输层可重试错误（-7、0x75） | 窗口内已被重试消化，结束时没有终态错误对象 |

参考项目 `sbi-bridge` 语义一致：`waitForFinger` 把 101 转为 null，其他错误透传，
超时统一返回 `102`（`CaptureService.java:140-143`、`192-202`、`275`）。
因此本轮不改错误码映射；对 1069/1082/1090 来说，101 与 102 都无法通过 CTK 的成功用例
schema（该 schema 的 `errorCode` 枚举只有 `0`），唯一路径是采集窗口内拿到帧。

## 3. 方案

### 3.1 采集截止预留响应余量（P0）

`SbiAuthenticationBridge.Device/FAP20Proxy.cs`：

- 新增常量：

  ```csharp
  /// <summary>
  /// 采集截止前预留的响应余量，保证响应在 CTK timeout 内到达
  /// </summary>
  private const int CaptureResponseMarginMs = 500;
  ```

- `CaptureNormalAsync`：

  ```csharp
  var deadline = Environment.TickCount64 + Math.Max(timeoutMs - CaptureResponseMarginMs, MinNativeTimeoutMs);
  ```

- 不改 `CaptureTimeoutTestAsync`（SBI1057 依赖 CTK 超时后的额外 10s 选帧窗口），
  不改 `CaptureMismatchAsync`（单帧直接返回）。

效果：正常采集最迟在 `timeout - 500ms` 结束并返回 102 或成功帧，
给 HTTP 写出和 CTK 侧开销留出余量。

### 3.2 采集过程摘要日志（P1，便于下一轮定位）

现状：判断“没按手指 / 质量不达标 / 设备错误”必须翻 Debug 级原始收发日志。

`FAP20Proxy` 注入可选 `ILogger<FAP20Proxy>?`（与 `FAP20` 的写法一致），
在 `CaptureNormalAsync` 返回点输出：

| 场景 | 级别 | 内容 |
|---|---|---|
| 成功 | Information | transactionId、轮询次数、质量分、耗时 |
| 无有效帧 | Warning | transactionId、轮询次数、无有效帧次数、质量不足次数、耗时 |

组合根 `SbiAuthenticationBridge.Desktop/FAP20Factory.cs` 在创建时传入
`ILogger<FAP20Proxy>`（现成 DI 解析，与其他服务一致）。

### 3.3 不做的事

- 不调整质量门限、不改 JWT 解析、不改签名与哈希逻辑。
- 不为 1069（ISO19794-4）和 1082（质量分）做盲改：本轮没有返回数据，
  校验器结论要等有数据后从 CTK 详情获取。
- 不修改 `FAP20Proxy` 中已有的 `Debug.WriteLine`（不在本 spec 范围）。

## 6. 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| 提前 500ms 结束采集 | 中 | 用户恰在最后 500ms 按压会拿到 102；摘要日志可直接识别该场景 |
| TimeCheck 计时口径假设 | 中 | 余量基于实测 0.46s 前置开销；若重跑仍判超时，按 CTK 详情再调整 |
| 注入 logger 改变构造参数 | 低 | 仅组合根一处调用点，可选参数保持兼容 |

## 7. 验证方式

1. 构建 Desktop，确认 0 warning / 0 error。
2. 重启应用。
3. 重跑 SBI1069 / SBI1082 / SBI1090，**在 CTK 提示期间按压指纹并保持到采集完成**。
4. 期望：
   - 响应包含 `data`、`hash`、`sessionKey`、`thumbprint`、`dataDecoded`；
   - 响应耗时小于 `timeout`；
   - 日志出现“采集成功”摘要，含轮询次数与质量分。
5. 若 1069 仍失败，按 CTK 的 `ISOStandardsValidator` 描述进入下一轮修复；
   若 1082 仍失败，按质量分摘要核对门限。
