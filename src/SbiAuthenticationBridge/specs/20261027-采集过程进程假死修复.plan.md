# Plan:采集过程中进程假死修复

> 对应 spec：`specs/20261027-采集过程进程假死修复.spec.md`
> 依据：`Logs/sbi-20261027.log` 的日志体量、`LogView.axaml` 的列表实现、arch.md。

## 1. 现象与复现

CTK 发起 CAPTURE 期间窗口无法操作，服务端仍正常响应，采集结束、日志停止刷新后恢复。

## 2. 根因

### 2.1 日志到 UI 的链路本身是异步的

`SerilogLogEntrySink` → `InMemoryLogEntryStore.Append` → `LogViewModel.OnEntryAdded`
只做入队与 `Dispatcher.UIThread.Post(..., Background)`，消费在 UI 线程批量执行。
**spec 里“日志未做异步”的猜测不是根因**，不需要改日志管线。

### 2.2 真正的瓶颈：日志列表没有虚拟化

`Views/LogView.axaml`：

```xml
<ScrollViewer>
    <ItemsControl ItemsSource="{Binding Entries}">
```

- `LogView` 固定在主窗口底部，**始终可见**；
- `ItemsControl` 默认面板是 `StackPanel`，在 `ScrollViewer` 里拿到无限高度，
  **不会虚拟化**，每条日志都会创建并测量一个控件；
- 缓冲上限 2000 条，每条新增都会触发整列表重新测量。

### 2.3 放大因素：单条日志可达 32KB

`FAP20.LogTextResponse` 把固件原始 TEXT 完整写入日志。
实测当天日志最大单行 **32,543 字符**（CAPTURE_AUTH / DEVICE_INFO 的 JWT）：

```text
32543 542
32529 546
...
```

这些大字符串进入内存缓冲后，由 `TextBlock`（`TextWrapping="Wrap"`）渲染。
测量 3 万字符的换行文本本身就要几十毫秒，叠加上千条历史的整体测量，
UI 线程在采集期间（约 10 条/秒）持续满载，输入事件得不到调度 → 假死。

## 3. 方案

### 3.1 日志列表虚拟化（P0）

`SbiAuthenticationBridge/Views/LogView.axaml`：

- `ItemsControl` 改为 `ItemsRepeater`（Avalonia 12.1 内置，`ItemsRepeater` 在
  `ScrollViewer` 内按可视区域创建元素）；
- 外部 `ScrollViewer` 与 `LogScrollViewer.ScrollToEnd()` 保持不变；
- 条目模板不变（时间 / 级别 / 消息 / 异常）。

### 3.2 不截断文本

界面继续完整渲染日志内容（含 32KB 的 JWT 条目），不做任何截断：

- 虚拟化后只有可视区域内的少量条目参与布局，历史大条目不再每次重排；
- 代价是滚动到某条超大日志时会多做一次该条目的布局（一次性开销），
  可能表现为轻微卡顿，但不会持续假死。

若实机验证后这个一次性卡顿仍不可接受，下一轮再引入“超长条目默认折叠、
点开看全文”的方案——仍然不丢内容，只是延迟渲染。

### 3.3 单次消费上限（P1）

`SbiAuthenticationBridge/ViewModels/LogViewModel.cs`：

- `DrainPending` 每轮最多消费 `MaxDrainPerPass = 500` 条，
  剩余继续走已有的“消费后重新调度”逻辑；
- 避免启动或错误风暴时单次 UI 操作过长。

### 3.4 不做的事

- 不降低 Serilog 级别、不改文件日志、不改 `FAP20` 原始收发日志的内容；
- 不改采集业务逻辑与错误码映射；
- 不改其他页面布局。

## 4. 文件清单

| 文件 | 改动 |
|---|---|
| `SbiAuthenticationBridge/Views/LogView.axaml` | `ItemsControl` → `ItemsRepeater` |
| `SbiAuthenticationBridge/ViewModels/LogViewModel.cs` | 单次消费上限 |

## 5. 架构与依赖自查

- 只触及 Presentation 层（View / ViewModel），无跨层调用；
- 无接口变更、无新增 NuGet（`ItemsRepeater` 属 Avalonia.Controls 内置控件）。

## 6. 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| `ItemsRepeater` 滚动到底行为差异 | 中 | 虚拟化后 extent 异步增长，需实机确认自动滚动仍贴底；必要时改用 `ScrollToEnd` 重试 |
| 超大条目一次性布局开销 | 中 | 不截断，滚动/新增大条目（约 32KB）时会做一次完整测量，可能出现轻微卡顿；若实测不可接受，下一轮改为“默认折叠、点开看全文” |
| 单次消费上限 | 低 | 剩余条目立即在下一轮消费，顺序不变 |

## 7. 验证方式

1. 构建 Desktop，确认 0 warning / 0 error。
2. 重启应用，保持日志页可见；用 CTK 发起一次 CAPTURE。
3. 观察：
   - 采集期间可正常切换控件/滚动日志/输入过滤关键字；
   - 日志持续刷新，采集结束无补写风暴；
   - 含 JWT 的大日志条目在界面完整显示（不截断），滚动到该条时允许一次轻微卡顿。
4. 采集完成后确认日志列表自动滚动到底部仍然生效。
