## 2. SBI1048 根因（真实回归）

上一轮为满足 SBI1090 的 TimeCheck 新增了 500ms 响应余量：

```csharp
var budgetMs = Math.Min(
    timeoutMs,
    Math.Max(timeoutMs - CaptureResponseMarginMs, MinNativeTimeoutMs));
```

SBI1048 的 `timeout=500ms`，代入后预算被压到 `MinNativeTimeoutMs=200ms`，
响应在 235ms 返回。

CTK 的 `TimeoutValidator` 对“无输入超时”用例要求**响应不能早于 timeout**：

```text
Timeout validation failed. Timeout given: 500 ms. Response received in: 235 ms
```

上一轮改动前该用例是通过的（响应约 500ms+）。

## 3. 方案

### 3.1 余量只对较长 timeout 生效

`SbiAuthenticationBridge.Device/FAP20Proxy.cs`：

- 新增常量：

  ```csharp
  /// <summary>
  /// 预留响应余量的最小 timeout；过短的超时用例必须等满 timeout
  /// </summary>
  private const int MinTimeoutForResponseMarginMs = 2_000;
  ```

- `CaptureNormalAsync` 截止时间：

  ```csharp
  var budgetMs = timeoutMs >= MinTimeoutForResponseMarginMs
      ? timeoutMs - CaptureResponseMarginMs
      : timeoutMs;
  var deadline = Environment.TickCount64 + budgetMs;
  ```

效果：

| timeout | 预算 | 说明 |
|---|---|---|
| 500ms（SBI1048） | 500ms | 等满超时，响应约 530ms ≥ 500ms |
| 10s（SBI1018 等） | 9.5s | 保留 500ms 余量，满足 TimeCheck |
| 20s（SBI1057 选帧路径） | 不变 | 走 `CaptureTimeoutTestAsync`，未受影响 |

### 3.2 不做的事

- 不为 SBI1018 / SBI1057 做代码改动：日志显示窗口内没有指纹输入，
  改服务端逻辑无法产生影响；需在重跑时按压指纹。
- 不改质量门限、不改错误码映射、不改 101 的等待语义。

## 6. 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| 短超时用例无余量 | 低 | 仅 SBI1048（500ms）使用短超时，CTK 要求等满 timeout |
| 长超时用例仍可能贴边 | 低 | 10s 用例响应约 9.5s，距边界 500ms；如实测仍有超时再加大余量 |

## 7. 验证方式

1. 构建 Desktop，确认 0 warning / 0 error。
2. 重启应用，重跑三个用例：
   - **SBI1048**：期望响应约 530ms，`TimeoutValidator` 通过，响应体仍为 102；
   - **SBI1018**：在 CTK 提示期间按压指纹并保持约 2s，期望返回 `data/hash/...`；
   - **SBI1057**：同样在提示期间按压，期望返回质量分最高的一帧。
3. 若 1018/1057 在确认按压的情况下仍全部返回 101，
   再按“设备未响应按压”方向采集原始 I/O 证据（0x75、传输错误、固件 102）。
