# Plan:CTK 验证与修复（第 4 轮）

> 对应 spec：`specs/20261026-CTK验证并修复-4.spec.md`
> 依据：SBI1018 CTK 请求/响应详情、SDK 运行日志、参考 sbi-bridge 采集实现。

## 0. 现象

SBI1018（以及 1019-1021、1069、1082、1090、1107）的响应都是：

```json
{"biometrics":[{"specVersion":"0.9.5","data":"","hash":"",
  "error":{"errorCode":"110","errorInfo":"Device is not ready"}}]}
```

CTK 的 SchemaValidator 因此报 `data/hash/sessionKey/thumbprint/dataDecoded` 缺失，
ResponseMismatchValidator 读取 `dataDecoded` 时 NPE，SignatureValidator 拿到空串。
**这些失败不是签名/解密/ISO 数据问题，而是采集根本没有发生。**

同时 SDK 日志存在：

```text
bulk transfer failed, endpoint=0x82 request=9 result=-7 transferred=0
Endpoint receive failed, endpoint = 0x82 cmd = 0x20, ret = -7
```

`0x20` 即 CAPTURE_AUTH，`-7` 是 libusb 超时。

## 1. 根因

1. `FAP20.ThrowIfFailed` 对**所有负返回码**一律 `CloseDevice()`，包括可恢复的
   `-7`（USB 传输超时）。
2. `FAP20Proxy.CaptureNormalAsync` 以 5 秒为一次原生采集轮询；用户放手指超过 5 秒，
   本次 `CAPTURE_AUTH` 返回 `-7`。
3. 于是设备句柄被关闭；后续采集在 `EnsureConnected` 抛
   `InvalidOperationException`，`MapDeviceFailure` 映射为 **110**。
4. 一次超时污染整个 CTK 会话：1018 失败后，1019-1021 等同路径全部 110。
   参考实现把采集侧的负返回视为“本轮未取到”，继续轮询；只有 `0x75` 才复位，
   **不会因超时关闭设备**。

这也解释了为什么 1048/1057（超时类用例）可以通过：它们不要求成功采集数据。

## 2. 修复方案

### 2.1 区分可恢复的 USB 超时

`SbiAuthenticationBridge.Device/FAP20.cs`

- 新增 `public const int UsbTimeoutResultCode = -7;`
- `ThrowIfFailed`：
  - `result == -7`：抛 `FtmCommandException` 说明命令超时，**不关闭设备**；
  - 其余负返回码保持现有语义：关闭句柄（设备可能已重新枚举）；
  - 正返回码保持现有语义（`0x75` 尝试软复位后抛错）。

### 2.2 采集轮询把 -7 当作“本轮未采到”

`SbiAuthenticationBridge.Device/FAP20Proxy.cs`

- `TryCaptureOnceAsync` 增加前置捕获：

  ```csharp
  catch (FtmCommandException exception)
      when (exception.ResultCode == FAP20.UsbTimeoutResultCode)
  {
      // 本轮等待手指超时，设备仍在线，继续轮询
      return null;
  }
  ```

- `CaptureNormalAsync`、`CaptureTimeoutTestAsync` 已把 `null` 视为继续等待，
  无需改动。
- 保留 5 秒轮询间隔与 200ms 重试间隔；保留每次采集前的域证书下发。

### 2.3 不修改

- 不改 SBI 路由、DTO、Core 契约。
- 不修改证书签名、JWT、域证书下发逻辑。
- 其他命令遇到 -7 时仍然向调用方报错，但不再断开设备。

## 3. 文件清单

| 文件 | 改动 |
|---|---|
| `SbiAuthenticationBridge.Device/FAP20.cs` | 新增 `UsbTimeoutResultCode = -7`；`ThrowIfFailed` 对 -7 不关设备 |
| `SbiAuthenticationBridge.Device/FAP20Proxy.cs` | 采集路径把 -7 当作“本轮未采到”，继续轮询 |

> 不新增 NuGet、不改架构分层。

## 4. 架构与依赖自查

- 改动全部位于 Device 基础设施层，不新增跨层依赖。
- 异常仍由 `FtmCommandException` 表达，Host 层行为不变。
- 不吞异常：`-7` 被明确识别并在采集轮询中转为“重试”，日志可追踪。

## 5. 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| -7 后固件可能仍持有半次采集，重试可能读到上一帧 | 中 | 保持 200ms 间隔与既有 `0x75` 复位逻辑；若复跑出现错帧，下一步改为“单次原生调用使用请求剩余超时” |
| 其他负返回码仍会断开设备 | 低 | 仅 -7 是 libusb 超时；-4/-1 等仍按原逻辑关闭 |
| 修复后 1069/1082/1090/1107 仍可能失败 | 中 | 这 4 个用例额外包含 ISO/质量/时间/hash 校验，需拿到成功采集响应后按实际 validator 结果处理 |
| 每次采集前 LOAD_CERT 增加耗时 | 低 | 已按协议顺序执行；-7 不再导致掉线 |

## 6. 验证方式

1. 构建 Desktop（temp OutDir，避免 DLL 占用）。
2. 重启应用并连接设备。
3. 发起一次采集，**故意等待 6 秒以上再放手指**：
   - 不应再出现 110；
   - 最终返回 `errorCode=0`，包含 `data/hash/sessionKey/thumbprint/dataDecoded`。
4. 连续发起两次采集，确认第一次超时不会导致第二次返回 110。
5. 重跑 CTK：
   - SBI1018-1021 应通过；
   - 观察 1069/1082/1090/1107 的失败描述，进入下一轮按 ISO/质量/时间/hash 定位。

## 7. 不在本次范围

- CTK 侧配置、域私钥。
- ISO 模板内容、qualityScore、timestamp、hash 链语义的修复（待真实成功响应）。
- USB 驱动/硬件链路。
