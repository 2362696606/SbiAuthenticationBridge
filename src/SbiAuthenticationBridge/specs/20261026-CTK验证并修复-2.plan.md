## 1. 根因

### 1.1 当前 DKL1 叶证书主题是占位值

当前运行中服务 `/info` 的 `deviceInfo` JWT x5c 叶证书：

```text
Subject: C=CN, S=Guangdong, L=Shenzhen, O=FTM-Test, OU=CCM-CCM4201S, CN=123456789012
Issuer : CN=ICT Global Synergy CTK Device Provider, O=Shenzhen ICT Global, ...
Valid  : 2026-10-26 .. 2027-01-24（有效）
签名   : 本地校验通过
```

来源是 `AppSetting.yaml` 的 `Dkl1Issuer` 占位配置：

```yaml
serialNo: "123456789012"
make: "CCM"
model: "CCM4201S"
deviceProvider: "FTM-Test"
```

真实设备身份（Discover/DeviceInfo 内的 digitalId）：

```text
serialNo: ICT-35195E304B513335
make: ICT Global
model: FCG3M
deviceProvider: Shenzhen ICT Global
```

### 1.2 CTK 校验逻辑

`SignatureValidator`（CTK 源码）：

1. `checkIfJWTSignatureIsValid`：x5c 首证书必须有效，签名必须用叶证书公钥验证通过；
2. `trustRootValidation(getCertificate(jwt), DEVICE/FTM, ...)`：证书链必须在对应信任域内；
3. 如果当前登录用户是 **DEVICE_PROVIDER** 角色：
   `validateOrgNameInCertificate` 要求叶证书 Subject 的 **O** 等于该 partner 的组织名；
4. 对 L1 设备，digitalId JWT 还要按 **FTM** 信任域再校验。

当前叶证书 O=`FTM-Test`，而 Provider 证书/设备 digitalId 的 provider 组织是
`Shenzhen ICT Global`；CTK 的组织名校验会失败。此前设备上的 fixture 叶证书
（历史采集样本 `CN=ICT FAP20 AA DKL1-A, O=Shenzhen ICT Global`）主题是正确的，
说明问题出在应用本地签发/密钥轮转使用了占位配置。

## 2. 修复方案

### 2.1 代码：DKL1 Subject 从设备身份派生

> 设备 digitalId 是 serialNo/make/model/deviceProvider 的**唯一权威来源**；`Dkl1Issuer` 不再保存这些身份字段。
> 之前把它们放进配置只是占位，正是本轮 O=FTM-Test 错误的来源。

修改 `DeviceOperateViewModel`：

1. 轮换前读取当前设备的 Discover 结果，解码未签名 `digitalId`（兼容单段/JWT 三段），得到：
   - `serialNo`、`make`、`model`、`deviceProvider`。
2. 叶证书 Subject：
   - `C=CN, S=Guangdong, L=Shenzhen`（与 Provider 证书保持一致）；
   - `O` = 设备 digitalId 的 `deviceProvider`；为空时回退到 Provider 证书 Subject 的 O；
   - `OU` = `{make}-{model}`；
   - `CN` = `serialNo`。
3. 设备发现失败、digitalId 缺失或身份字段不完整时：
   - 不签发证书；
   - 记录 `Error` 并把明确错误显示在界面上（例如“无法读取设备 digitalId，不能生成 DKL1 证书”）；
   - **不再回退到本地配置**，避免再次签发错误 Subject。
4. `RotateKeyAsync` 先解析身份，再签发、下发证书；不修改设备返回的公钥与已签名数据。

### 2.2 配置精简：只保留证书输出路径

`Dkl1IssuerOptions` 删除 `SerialNo/Make/Model/DeviceProvider`，仅保留 `IssuedCertificatePath`；
`SbiAuthenticationBridge.Desktop/Config/AppSetting.yaml` 同步精简：

```yaml
Dkl1Issuer:
  issuedCertificatePath: "E:/code/git/SbiAuthenticationBridge/src/SbiAuthenticationBridge/SbiAuthenticationBridge.Host/device-provider/dkl1_device.cer"
```

- `IsKeyRotationConfigured`/`KeySubjectDescription` 不再依赖身份配置：轮换按钮的可用性只取决于设备是否可用且实现 `IFtmSecureDevice`；
- 视图中的“签发材料未配置”提示与静态 Subject 描述相应移除/改为通用说明。

### 2.3 设备状态：重新轮换一次密钥

当前设备上的叶证书仍是错误的 `O=FTM-Test`。修复后必须：

1. 重启应用（加载新代码/配置）；
2. 在 DeviceOperateView 执行一次“轮换密钥”，让设备安装 subject 正确的新 DKL1 叶证书；
3. 通过 `/info` 确认新叶证书：
   - `O=Shenzhen ICT Global`
   - `CN=ICT-35195E304B513335`
   - `OU=ICT Global-FCG3M`
   - 签名/有效期正常。

否则 CTK 在 SBI1001/1026/采集用例仍会使用旧的错误证书。

## 4. 架构与依赖自查

- `Dkl1IssuerOptions` 精简属于 Core 契约变更（中风险，仅保留输出路径）。
- 其余改动在表现层 ViewModel/视图与本地配置。
- `DigitalId`/`DiscoveryRequest` 均来自 Core；不引用 Device/Host 实现。
- 证书签发仍使用 `CertificateSigner` 与组合根注入的 `ICertificateProvider`。
- 不伪造签名/证书链；O 取真实设备/Provider 身份。

## 5. 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| 设备未重新轮换，仍使用旧错误证书 | 高 | 修复后必须执行一次轮换并确认 `/info` 叶证书主题 |
| CTK 仍要求 FTM 信任域 | 中 | L1 digitalId 使用 Suzhou CCore FTM fixture 证书；若 CTK 项目未配置对应 FTM 信任，需在 CTK 侧配置（非本仓库代码） |
| 设备 digitalId 不可用 | 中 | 不回退配置；轮换明确失败并提示，避免签发错误证书 |
| 组织名仍与 CTK partner 不一致 | 中 | 以设备 digitalId.deviceProvider / Provider 证书 O 为准；如 CTK partner 组织不同，需以 CTK 项目配置为准 |
| Core `Dkl1IssuerOptions` 精简 | 中 | 仅保留输出路径；需同步更新 AppSetting 与视图文案 |

## 7. 验证方式

1. 构建 Shared/Desktop/Android/iOS/Browser。
2. 重启应用并执行一次密钥轮换，然后用 `MOSIPDINFO` 抓取 `/info`：
   - x5c 叶证书 Subject 为 `O=Shenzhen ICT Global, OU=ICT Global-FCG3M, CN=ICT-35195E304B513335`；
   - 确认这些值来自设备 digitalId 而非 AppSetting；
   - JWT 签名用叶证书公钥验证通过。
3. 用 Python `jsonschema` 重新校验 `/device`、`/info` 与采集样本 Schema（保持通过）。
4. 重新运行 CTK：SBI1001/1026/1024 与采集类用例应通过；如仍失败，根据 CTK 详细 validator 描述继续定位（重点 FTM 信任域）。
